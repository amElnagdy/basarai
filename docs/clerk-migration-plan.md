# Clerk Migration Plan — Supabase Auth → Clerk

**Scope:** replace Supabase Auth with Clerk. Keep email + password, add magic link (Clerk "email verification link").
**Out of scope:** brands, kits, provider keys, generations — their tables, routers, and UI do not change. Supabase stays as the database, storage, and vault.
**Data migration:** none. No real users exist; the `auth.users` table is abandoned, not migrated.
**Reviewed:** plan v1 debated with Codex (read-only, 2026-08-23); its blockers/should-fixes are folded in below and marked ⟲ where they changed a decision.

---

## 1. Where auth lives today (the seams)

| Seam | File(s) | What it does now |
|---|---|---|
| Frontend session | `frontend/lib/supabase/{client,server}.ts` | `@supabase/ssr` cookie session |
| Frontend gate | `frontend/middleware.ts` | `supabase.auth.getUser()` → redirect to `/login` or `/brands` |
| Frontend pages | `app/(auth)/login/page.tsx`, `app/(auth)/signup/page.tsx`, `app/auth/confirm/route.ts` | `signInWithPassword`, `signUp` + email confirm via `verifyOtp` |
| Frontend server components | `app/page.tsx`, `app/(dashboard)/[brandId]/{layout,page}.tsx`, `app/(dashboard)/admin/layout.tsx` | read session → forward `access_token` to backend |
| Frontend API client | `lib/api.ts` | `getSession().access_token` → `Authorization: Bearer`; on 401 `signOut()` |
| Frontend logout | `components/layout/app-sidebar.tsx` | `supabase.auth.signOut()` |
| Frontend proxy | `app/api/brands/[brandId]/generate/route.ts` | forwards whatever bearer it gets — **no change needed** |
| Backend token check | `backend/app/core/auth.py` | `PyJWKClient` on Supabase JWKS, `aud=authenticated`, claims `sub` + `email` → `User(id, email, access_token)` |
| Backend config | `backend/app/config.py`, `backend/tests/conftest.py` | `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `ADMIN_EMAILS`; conftest seeds only the Supabase vars |
| DB link to `auth.users` | `supabase/migrations/00002_create_profiles.sql`, `00003_create_brands.sql`, `00010_auto_create_profile_trigger.sql` | `profiles.user_id → auth.users(id)`, `brands.owner_user_id → auth.users(id)`, trigger `on_auth_user_created` |
| RLS | `00008_add_rls_policies.sql`, `00009_create_storage_bucket.sql` | policies on `auth.uid()` (backend uses the service key, so these never gate backend traffic) |
| Build/run | `Dockerfile`, `Makefile`, `scripts/container-entrypoint.sh`, `frontend/.env.local(.example)`, `backend/.env(.example)` | `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` build args; entrypoint validates Supabase runtime vars |
| Docs that describe auth | `CLAUDE.md`, `AGENTS.md`, `README.md`, `docs/docker.md` | Supabase Auth setup, redirect URLs, JWKS notes — will go stale |

Everything else (`brands.py`, `kit.py`, `keys.py`, `generations.py`, `admin.py`, all brand/kit/key/generation components, the `admin_*` views in `00014`) only consumes `User.id` / `User.email` from `get_current_user`. Those stay untouched because the `User` shape stays the same.

**Not an auth dependency, easy to break by accident:** `frontend/next.config.mjs` builds `images.remotePatterns` from `NEXT_PUBLIC_SUPABASE_URL`, and the backend keeps returning Supabase Storage URLs for logos and generations. That env var **stays** (⟲). Only the publishable key and the Supabase JS SDKs go.

## 2. The one design decision: user IDs

Clerk user IDs are strings (`user_2abc…`), not UUIDs. `brands.owner_user_id` is `UUID` and must not change. So:

- `profiles.user_id` stays a **UUID primary key**, now generated by Postgres (`DEFAULT gen_random_uuid()`).
- `profiles` gains `clerk_user_id TEXT UNIQUE NOT NULL` — the mapping Clerk → internal UUID.
- `brands.owner_user_id` is re-pointed from `auth.users(id)` to `profiles(user_id)` (same type, same `ON DELETE CASCADE`).
- The backend resolves `sub` (Clerk ID) → `profiles.user_id` on every request, creating the profile on first sight ("just-in-time provisioning"). This replaces the `on_auth_user_created` trigger and needs no webhook, which matters because local Docker has no public URL for Clerk to call.
- `User.id` handed to routers is still the internal UUID. Nothing downstream changes.

Known semantic shift: deleting a user in Clerk no longer cascades anywhere (no trigger). Acceptable while there are no real users; a `user.deleted` webhook is the later fix.

Rejected alternatives: (a) change `owner_user_id` to TEXT — touches brands, violates scope; (b) Clerk webhook for provisioning — needs a public endpoint and Svix verification, overkill for now.

### Step 1 — Database: `supabase/migrations/00015_clerk_auth.sql`

```sql
-- 0. guard: this migration assumes no data (no users exist yet)
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM profiles) OR EXISTS (SELECT 1 FROM brands) THEN
    RAISE EXCEPTION 'clerk migration expects empty profiles/brands; found rows';
  END IF;
END $$;

-- 1. stop depending on auth.users
DROP TRIGGER IF EXISTS on_auth_user_created ON auth.users;
DROP FUNCTION IF EXISTS handle_new_user();

-- 2. profiles: internal UUID stays PK, now self-generated; add Clerk id
ALTER TABLE profiles
  DROP CONSTRAINT profiles_user_id_fkey,
  ALTER COLUMN user_id SET DEFAULT gen_random_uuid(),
  ADD COLUMN clerk_user_id TEXT NOT NULL UNIQUE;
COMMENT ON TABLE  profiles IS 'User profile information - one row per Clerk user';
COMMENT ON COLUMN profiles.user_id IS 'Internal user ID (UUID) — referenced by brands.owner_user_id';
COMMENT ON COLUMN profiles.clerk_user_id IS 'Clerk user ID (JWT sub claim)';

-- 3. brands: re-point the FK to profiles (column type unchanged)
ALTER TABLE brands
  DROP CONSTRAINT brands_owner_user_id_fkey,
  ADD CONSTRAINT brands_owner_user_id_fkey
    FOREIGN KEY (owner_user_id) REFERENCES profiles(user_id) ON DELETE CASCADE;
```

Notes:
- ⟲ No regex on `clerk_user_id` (don't couple to Clerk's ID format; the JWT signature is the guarantee). No `TRUNCATE` escape hatch — the guard aborts instead; if it fires, clean up by hand and rerun.
- Constraint names are Postgres defaults from `00002`/`00003`; confirm with `\d profiles` / `\d brands` before pushing.
- RLS and storage policies using `auth.uid()` stay as-is: they evaluate to `NULL` → deny for any non-service client (browser holds no Supabase session any more), while the backend's service key bypasses them. Public storage reads stay public by design.
- `admin_stats` / `admin_brand_overview` (`00014`) join on `profiles.user_id` — unaffected.
- Apply with `supabase db push`.

### Step 2 — Backend: `backend/app/core/auth.py` + `config.py`

`config.py` — add:
```python
CLERK_ISSUER: str                 # https://<frontend-api-host>  (JWKS = f"{CLERK_ISSUER}/.well-known/jwks.json")
CLERK_AUTHORIZED_PARTIES: str     # REQUIRED, comma-separated origins, e.g. http://localhost:3001,http://localhost:3000,https://app.example.com
```
⟲ Single issuer setting (JWKS derived — two independent settings can point at two instances). ⟲ `azp` allow-list is **required**, not optional: Clerk documents that skipping authorized-party checks opens subdomain-cookie/CSRF attacks. `SUPABASE_URL` / `SUPABASE_SECRET_KEY` stay (DB, storage, vault).

`auth.py`:
1. `_jwks_client = PyJWKClient(f"{settings.CLERK_ISSUER}/.well-known/jwks.json", cache_jwk_set=True, lifespan=3600, timeout=5)`.
2. `jwt.decode(token, key, algorithms=["RS256"], issuer=settings.CLERK_ISSUER, leeway=5, options={"verify_aud": False, "require": ["exp", "nbf", "iat", "iss", "sub"]})`. Then: `azp` present and in `CLERK_AUTHORIZED_PARTIES`, else 401; `sub` and `email` non-empty strings, else 401 `INVALID_TOKEN`. Same error envelope as today.
3. ⟲ Error separation: `PyJWTError` → 401. JWKS fetch failure / Supabase failure during profile lookup → **503/500**, never disguised as `INVALID_TOKEN`. Log invalid tokens at `warning` without a stack trace and never log the bearer value.
4. `resolve_profile(clerk_id) -> str`:
   - `select user_id from profiles where clerk_user_id = :sub` (unique index);
   - on miss: `client.table("profiles").upsert({"clerk_user_id": sub}, on_conflict="clerk_user_id", ignore_duplicates=True)` then re-select — race-safe (two first requests: one inserts, the other finds it). ⟲ No in-process cache until measured.
5. ⟲ `User` model slims to `id: str` (internal UUID, same meaning as today) + `email: str`. `access_token` has no consumer — drop it; don't add `clerk_id` until something needs it. Routers unchanged.
6. `get_current_admin_user` unchanged.
7. `me.py`: `PROFILE_NOT_FOUND` becomes unreachable for GET; leave as a defensive branch.
8. `backend/tests/conftest.py`: ⟲ `os.environ.setdefault` for `CLERK_ISSUER` and `CLERK_AUTHORIZED_PARTIES` before `from app.main import app`, otherwise the whole suite fails at import.
9. `backend/.env.example`: add the two `CLERK_*` vars and `CLERK_SECRET_KEY` (consumed by the Next server, see Step 4).

Alternative considered: `clerk-backend-api` SDK (`authenticate_request`) — equivalent checks, extra dependency; PyJWT is already present. Calling Clerk's Users API per request for the email: rate-limited and slower than the claim.

## 6. Deliberately not done

- Webhooks (`user.created` / `user.deleted`): JIT covers creation; deletion leaves an orphan profile until a webhook exists.
- Tightening RLS from `auth.uid()` to `false` (cosmetic; service key bypasses it).
- Replacing the hand-built login/signup UI with Clerk's prebuilt `<SignIn/>`/`<SignUp/>` (faster, but discards the current design and the upcoming design episode).
- Cross-device magic links, social logins, MFA, organizations, Next 15 upgrade.
- Touching `specs/*` or historical migrations.
